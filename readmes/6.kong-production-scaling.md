# Kong — Production Deployment & Scaling
> How to host Kong the right way, scale it when traffic spikes, and never lose sleep over it.

---

## Read This First — The Big Picture

You already know Kong sits in the middle between your clients and your apps.
Now the question is: **how do you run Kong itself in production, at scale, without it becoming a single point of failure?**

The answer has two parts:

```
Part 1 — How Kong stores its config (DB Mode vs DB-less)
Part 2 — How Kong scales horizontally when traffic spikes
```

And the beautiful thing is:

```
Kong nodes are STATELESS.

All config lives in PostgreSQL.
A new Kong node starts → connects to Postgres → gets full config → starts serving.
You can add or remove Kong nodes freely. Zero manual config per node.
```

This is what makes horizontal scaling trivial.

```
                          Internet
                              │
                   ┌──────────▼──────────┐
                   │    AWS ALB / NLB     │  ← terminates TLS (HTTPS)
                   │  (or GCP / Azure LB) │    distributes across Kong nodes
                   └──────────┬──────────┘
                              │
           ┌──────────────────┼──────────────────┐
           ▼                  ▼                  ▼
     ┌───────────┐      ┌───────────┐      ┌───────────┐
     │  Kong  1  │      │  Kong  2  │      │  Kong  3  │
     │  :8000    │      │  :8000    │      │  :8000    │

           │                  │                  │

                              │  all nodes share one config store
                   ┌──────────▼──────────┐

                   └─────────────────────┘

                   ┌──────────▼──────────┐

                   └─────────────────────┘

Kong Admin API (port 8001) — NEVER exposed to internet
Only reachable from your VPC / CI runner / bastion host
```

## Part 1 — DB Mode vs DB-less Mode

### DB Mode (PostgreSQL) ← Production Choice

```
deck sync kong.yml
      │
      ▼
Kong Admin API (port 8001)
      │
      ▼
PostgreSQL  ← stores all config
      │
      ├── Kong Node 1  reads config from here
      ├── Kong Node 2  reads config from here
      └── Kong Node 3  reads config from here
```

- Every Kong node reads config from the shared Postgres
- `deck sync` pushes your YAML to Postgres once — all nodes pick it up within seconds
- Full Kong Manager UI available
- Full decK support
- **This is what you use when Kong is a shared service for your company**

### DB-less Mode (Declarative Only)

```
kong.yml baked into Docker image
      │
      ▼
Kong Node 1  ← loads YAML at startup
Kong Node 2  ← loads YAML at startup
Kong Node 3  ← loads YAML at startup
```

- No Postgres at all
- Config change = rebuild image + redeploy all nodes
- No Kong Manager UI
- Good for simple setups, bad for a shared company gateway
- **Not recommended when multiple teams are configuring Kong**

> **Decision: Use DB Mode for your company's Kong deployment.**
> You want hot config changes, the UI, and decK + GitOps without redeploying Kong itself.

## Part 2 — The Three Deployment Paths

There are three ways to run Kong in production.
Each has a different scaling story.

```
Path 1 → EC2 + Auto Scaling Group (ASG)       ← simplest, VM-based
Path 2 → EKS (Kubernetes) + HPA               ← cloud-native, recommended
Path 3 → ECS Fargate                           ← serverless containers, no node management
```

---

## Path 1 — EC2 + Auto Scaling Group (ASG)

### What it is

You run Kong on EC2 virtual machines.
AWS Auto Scaling Group automatically adds or removes EC2 instances based on load.

### How it works

```
                    AWS ALB (Application Load Balancer)
                           │
                           │  distributes traffic
                    ┌──────▼──────┐
                    │     ASG     │  ← Auto Scaling Group
                    │  min: 2     │    watches CPU / RPS
                    │  max: 10    │    adds EC2s when load spikes
                    └──────┬──────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    ┌──────────┐     ┌──────────┐     ┌──────────┐
    │  EC2 #1  │     │  EC2 #2  │     │  EC2 #3  │  ← new one added by ASG
    │  Kong    │     │  Kong    │     │  Kong    │
    └──────────┘     └──────────┘     └──────────┘
          │                │                │
          └────────────────┼────────────────┘
                           │
                      RDS PostgreSQL
```

### The Launch Template (what each EC2 runs on boot)

```bash
#!/bin/bash
# This script runs automatically when ASG launches a new EC2

# Install Kong (already baked into AMI ideally — this is fallback)
apt-get update -y
apt-get install -y kong-enterprise-edition

# Write kong.conf pointing to shared RDS
cat > /etc/kong/kong.conf <<EOF
database = postgres
pg_host = your-rds-endpoint.rds.amazonaws.com
pg_port = 5432
pg_database = kong
pg_user = kong
pg_password = ${KONG_DB_PASSWORD}   # pulled from AWS Secrets Manager
proxy_listen = 0.0.0.0:8000
admin_listen = 127.0.0.1:8001       # NEVER 0.0.0.0 in production
EOF

# Start Kong — it connects to RDS, gets full config, starts serving
kong start
```

### ASG Scaling Policy

```
Scale OUT (add EC2):
  Trigger: CPU > 60% for 2 minutes
  Action:  Add 1 EC2 instance
  Cooldown: 3 minutes (don't add another until this one is healthy)

Scale IN (remove EC2):
  Trigger: CPU < 30% for 10 minutes
  Action:  Remove 1 EC2 instance
  Cooldown: 5 minutes (be conservative removing — don't thrash)

Minimum instances: 2   ← always have 2 for HA, never go to 1
Maximum instances: 10  ← cost cap
```

### When to use EC2 + ASG

- You're not on Kubernetes yet
- Simpler ops, your team knows EC2
- Lift-and-shift from bare metal
- Good starting point before moving to EKS

## Path 2 — EKS (Kubernetes) + HPA ← Recommended

### What it is

You run Kong as pods inside a Kubernetes cluster on AWS EKS.
Kubernetes HPA (Horizontal Pod Autoscaler) automatically adds or removes Kong pods based on load.

### Why this is the recommended path

```
EC2 + ASG                          EKS + HPA
──────────────────────────────     ──────────────────────────────
Scale in minutes (EC2 boot time)   Scale in seconds (pod start time)
Manual AMI management              Image-based, GitOps-friendly
SSH into machines to debug         kubectl logs / exec
Hard to do canary deploys          Native canary, blue/green
No self-healing                    Pod crashes → Kubernetes restarts it
```

### The Full EKS Architecture

```
                    AWS ALB Ingress Controller
                    (or AWS NLB for Layer 4)
                           │
                    ┌──────▼──────┐
                    │  Kong Pods  │  ← Kubernetes Deployment
                    │  replicas:3 │    HPA scales this up/down
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  RDS Postgres│  ← outside the cluster
                    │  Multi-AZ   │    in the same VPC
                    └─────────────┘
                           │
                    ┌──────▼──────┐
                    │   Redis      │  ← ElastiCache
                    │ (rate limits)│
                    └─────────────┘
```

### Installing Kong on EKS with Helm

Kong has an official Helm chart. This is the standard way to deploy it.

```bash
# Step 1 — Add the Kong Helm repo
helm repo add kong https://charts.konghq.com
helm repo update

# Step 2 — Create namespace
kubectl create namespace kong

# Step 3 — Create a secret for the Postgres password
# Never hardcode passwords in values.yaml
kubectl create secret generic kong-postgres-secret \
  --namespace kong \
  --from-literal=pg_password="your_strong_password_here"

# Step 4 — Install Kong
helm install kong kong/kong \
  --namespace kong \
  --values kong-values.yaml
```

### kong-values.yaml — The Helm Configuration

```yaml
# kong-values.yaml
# This is your single source of truth for the Kong deployment on EKS

image:
  repository: kong/kong-gateway
  tag: "3.6"                        # pin to a specific version, never use latest

# ── REPLICAS ──────────────────────────────────────────────────────────────────
replicaCount: 3                     # start with 3 pods across 3 AZs
                                    # HPA will scale this up automatically

# ── DATABASE ──────────────────────────────────────────────────────────────────
env:
  database: postgres
  pg_host: your-rds-endpoint.rds.amazonaws.com
  pg_port: 5432
  pg_database: kong
  pg_user: kong
  pg_password:
    valueFrom:
      secretKeyRef:
        name: kong-postgres-secret  # Kubernetes secret — never plain text
        key: pg_password

  # ── PORTS ─────────────────────────────────────────────────────────────────
  proxy_listen: "0.0.0.0:8000"
  admin_listen: "0.0.0.0:8001"     # safe inside cluster — not exposed externally
  status_listen: "0.0.0.0:8100"   # health check endpoint for Kubernetes probes

  # ── PERFORMANCE ───────────────────────────────────────────────────────────
  nginx_worker_processes: auto      # one worker per CPU core
  mem_cache_size: 256m

# ── PROXY SERVICE (how traffic enters Kong) ───────────────────────────────────
proxy:
  enabled: true
  type: LoadBalancer                # AWS creates an NLB automatically
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"

# ── ADMIN SERVICE (internal only — never internet-facing) ─────────────────────
admin:
  enabled: true
  type: ClusterIP                   # only reachable inside the cluster
                                    # your CI/CD runner uses kubectl port-forward to reach it

# ── HEALTH CHECKS (Kubernetes uses these to know if a pod is ready) ───────────
readinessProbe:
  httpGet:
    path: /status
    port: 8100
  initialDelaySeconds: 15
  periodSeconds: 10

livenessProbe:
  httpGet:
    path: /status
    port: 8100
  initialDelaySeconds: 30
  periodSeconds: 10

# ── RESOURCES (always set limits — never let a pod consume unlimited memory) ──
resources:
  requests:
    cpu: "500m"                     # 0.5 CPU cores guaranteed
    memory: "512Mi"                 # 512MB guaranteed
  limits:
    cpu: "2000m"                    # max 2 CPU cores
    memory: "1Gi"                   # max 1GB — Kong will OOM-kill before taking the node down

# ── POD DISRUPTION BUDGET (never let all pods go down during a rolling update) ─
podDisruptionBudget:
  enabled: true
  minAvailable: 2                   # always keep at least 2 pods running
```


### HPA — Horizontal Pod Autoscaler

This is the Kubernetes object that watches Kong's CPU/memory and adds pods automatically.

```yaml
# hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: kong-hpa
  namespace: kong
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: kong-kong                 # the deployment name Helm creates

  minReplicas: 3                    # never go below 3 (HA across 3 AZs)
  maxReplicas: 20                   # cost cap — tune based on your budget

  metrics:
    # Scale on CPU — most common trigger for Kong
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60    # when average CPU across all pods hits 60%, add pods

    # Scale on memory too — Kong caches routes/plugins in memory
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 70

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60    # wait 60s before scaling up again
      policies:
        - type: Pods
          value: 2                       # add max 2 pods at a time
          periodSeconds: 60

    scaleDown:
      stabilizationWindowSeconds: 300   # wait 5 minutes before scaling down
      policies:
        - type: Pods
          value: 1                       # remove max 1 pod at a time (conservative)
          periodSeconds: 120
```

### How a traffic spike plays out on EKS

```
Normal traffic:
  3 Kong pods running, CPU at 30%

Traffic spike hits:
  CPU climbs to 65% across all pods
  HPA detects: average CPU > 60%
  HPA adds 2 pods (per scaleUp policy)
  New pods start in ~10 seconds
  Connect to RDS → get full config → start serving
  CPU drops back to ~40%

Spike ends:
  CPU drops to 20%
  HPA waits 5 minutes (stabilizationWindowSeconds)
  Removes 1 pod
  Waits 2 more minutes
  Removes 1 more pod
  Back to 3 pods
```

### Spreading pods across Availability Zones

Always spread Kong pods across multiple AZs. If one AZ goes down, the others keep serving.

```yaml
# Add this to your Helm values or Kong deployment
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values:
                - kong
        topologyKey: topology.kubernetes.io/zone
        # This FORCES Kubernetes to put each Kong pod in a different AZ
        # If you only have 2 AZs, use preferredDuringScheduling instead
```

## Path 3 — ECS Fargate

### What it is

AWS Fargate runs your containers without you managing any EC2 instances.
You define the task (container + CPU + memory), Fargate runs it.
ECS (Elastic Container Service) manages the scheduling and scaling.

```
You define:  "Run Kong container, 1 vCPU, 2GB RAM"
Fargate:     Finds capacity, runs it, scales it, patches the host OS
You never:   SSH into a machine, patch an OS, manage a node
```

### When to use Fargate

- You don't want to manage EC2 nodes at all
- Smaller team, less ops overhead
- Pay per second of container runtime (can be cheaper at variable load)
- Not on Kubernetes yet but want container-native scaling

### ECS Service Auto Scaling

```
ECS Service
  desiredCount: 3
  min: 2
  max: 15

  Scaling policy:
    Metric: ECSServiceAverageCPUUtilization
    Target: 60%
    Scale out: add 2 tasks when CPU > 60%
    Scale in:  remove 1 task when CPU < 30% for 10 minutes
```

## The Load Balancer Layer — ALB vs NLB

The load balancer sits in front of all Kong nodes/pods and distributes traffic.

```
ALB (Application Load Balancer) — Layer 7
  ├── Understands HTTP/HTTPS
  ├── Can route by path, header, host
  ├── SSL termination here (Kong receives plain HTTP internally)
  ├── Better for HTTP APIs
  └── Use this for most Kong deployments

NLB (Network Load Balancer) — Layer 4
  ├── Understands TCP/UDP only
  ├── Extremely low latency (microseconds)
  ├── Preserves client IP natively
  ├── Better for high-throughput, low-latency requirements
  └── Use this when you need WebSocket or gRPC at scale
```

### ALB with Kong on EKS

```yaml
# AWS Load Balancer Controller annotation on Kong's Service
service:
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/healthcheck-path: /status
    alb.ingress.kubernetes.io/healthcheck-port: "8100"
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:region:account:certificate/xxx
    # ↑ your SSL cert from AWS Certificate Manager — ALB terminates TLS
```

## HAProxy — What It Is and Where It Fits

### What is HAProxy?

HAProxy is a battle-tested, high-performance TCP/HTTP load balancer and proxy.
It has been around since 2000 and is used by some of the largest sites in the world.

```
HAProxy is NOT a replacement for Kong.
HAProxy is NOT an API gateway.

HAProxy is a load balancer.
Kong is an API gateway.

They solve different problems.
```

### Where HAProxy fits with Kong

```
Option A — HAProxy in front of Kong (instead of ALB/NLB)

Internet
   │
   ▼
HAProxy  ← load balances across Kong nodes, health checks, SSL termination
   │
   ├── Kong Node 1
   ├── Kong Node 2
   └── Kong Node 3
          │
       Your Apps


Option B — HAProxy in front of your apps (Kong still in the middle)

Internet
   │
   ▼
ALB / NLB
   │
   ▼
Kong  ← API gateway (auth, rate limit, routing)
   │
   ▼
HAProxy  ← load balances across your app instances
   │
   ├── App Instance 1
   ├── App Instance 2
   └── App Instance 3
```

### Why you might choose HAProxy over ALB/NLB

```
HAProxy                              ALB/NLB
──────────────────────────────       ──────────────────────────────
Self-hosted, no AWS dependency       AWS-managed, no ops overhead
Extremely fine-grained config        Simpler config
Free (open source)                   Costs money per LCU
Works on-prem or any cloud           AWS only
Requires you to manage HA for it     AWS handles HA automatically
```

### HAProxy config for Kong (the basics)

```
# haproxy.cfg

frontend kong_frontend
    bind *:80
    bind *:443 ssl crt /etc/ssl/certs/your-cert.pem
    default_backend kong_nodes

backend kong_nodes
    balance roundrobin                    # distribute evenly across Kong nodes
    option httpchk GET /status            # health check Kong's status endpoint
    http-check expect status 200

    server kong1 10.0.1.10:8000 check inter 5s rise 2 fall 3
    server kong2 10.0.1.11:8000 check inter 5s rise 2 fall 3
    server kong3 10.0.1.12:8000 check inter 5s rise 2 fall 3
    # inter 5s   = check every 5 seconds
    # rise 2     = 2 consecutive successes = mark healthy
    # fall 3     = 3 consecutive failures  = mark unhealthy, stop sending traffic
```

> **For a cloud deployment on AWS/GCP/Azure: use the managed load balancer (ALB/NLB).**
> HAProxy makes more sense when you're on-prem or need very specific LB behavior the cloud LB can't do.

## Envoy Proxy — What It Is and Where It Fits

### What is Envoy?

Envoy is a modern, high-performance proxy originally built by Lyft.
It is the proxy that powers Istio (the most popular service mesh) and is also the foundation of the Envoy Gateway project.

```
Envoy is a proxy / data plane.
It is NOT an API gateway by itself.
It becomes one when paired with a control plane.
```

### The Envoy Ecosystem

```
Envoy Proxy (the engine)
      │
      ├── Istio          ← service mesh control plane (mTLS, traffic policies between services)
      ├── Envoy Gateway  ← Kubernetes Gateway API implementation (ingress + API gateway)
      └── Contour        ← another Kubernetes ingress controller built on Envoy
```

### Envoy Gateway — The New Kid

Envoy Gateway is a project that implements the Kubernetes Gateway API spec using Envoy as the data plane.
It is relatively new (GA in 2024) and is positioned as a simpler alternative to Kong/NGINX for teams already deep in Kubernetes.

```
Kubernetes Gateway API
      │
      ▼
Envoy Gateway (control plane)
      │
      ▼
Envoy Proxy pods (data plane — the actual traffic handler)
```

### Kong vs Envoy Gateway — Honest Comparison

```
                    Kong                    Envoy Gateway
────────────────────────────────────────────────────────────────
Maturity            10+ years               ~2 years (GA 2024)
Plugin ecosystem    500+ plugins            Limited, growing
Auth plugins        Built-in (key-auth,     Needs external auth service
                    JWT, OAuth, OIDC)       or custom Lua/WASM filters
Rate limiting       Built-in plugin         Needs custom filter or
                                            external service
Admin UI            Kong Manager (GUI)      No GUI — YAML only
decK / GitOps       Native support          Kubernetes manifests
Config style        YAML via decK           Kubernetes CRDs
Learning curve      Moderate                Steeper (K8s-native only)
Best for            API gateway as a        Teams fully on K8s who
                    service, multi-team     want native K8s primitives
```

### Where Envoy fits in YOUR architecture

If your company is fully on Kubernetes and wants everything as Kubernetes objects:

```yaml
# Envoy Gateway style — everything is a Kubernetes CRD
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: company-gateway
spec:
  gatewayClassName: eg              # eg = Envoy Gateway class
  listeners:
    - name: http
      port: 80
      protocol: HTTP
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app-route
spec:
  parentRefs:
    - name: company-gateway
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /api
      backendRefs:
        - name: my-app-service
          port: 3000
```

> **For your company's use case (Kong as a service, multiple teams, decK + GitOps):**
> **Stick with Kong. Envoy Gateway is a valid future consideration but Kong is more mature for this exact use case.**

## High Availability (HA) — Making Sure Kong Never Goes Down

HA means: **no single point of failure anywhere in the stack.**

### The HA Checklist

```
Layer               What can fail?          How to fix it
──────────────────────────────────────────────────────────────────────
Load Balancer       LB goes down            Use managed LB (ALB/NLB) — AWS runs it
Kong Nodes          One pod/EC2 crashes      Run minimum 3 nodes across 3 AZs
PostgreSQL          DB goes down             RDS Multi-AZ — automatic failover in ~60s
Redis               Redis goes down          ElastiCache with replication group
Config sync         deck sync fails          Rate limits fall back to local (fault_tolerant: true)
```

### RDS Multi-AZ — How it works

```
Primary RDS (AZ-a)  ←── Kong nodes write config here
      │
      │  synchronous replication
      ▼
Standby RDS (AZ-b)  ←── exact copy, ready to take over

If AZ-a fails:
  AWS automatically promotes standby to primary
  DNS endpoint stays the same
  Kong reconnects automatically
  Downtime: ~60 seconds
```

### Redis HA — ElastiCache Cluster Mode

```
Redis Primary  ←── Kong writes rate limit counters here
      │
      ├── Redis Replica 1  (AZ-b)
      └── Redis Replica 2  (AZ-c)

If primary fails:
  ElastiCache promotes a replica automatically
  Kong reconnects
  Some counters may reset (acceptable — fault_tolerant: true handles this)
```

### The Pod Disruption Budget (PDB) — Never lose all pods at once

```yaml
# pdb.yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: kong-pdb
  namespace: kong
spec:
  minAvailable: 2                   # Kubernetes MUST keep at least 2 Kong pods running
  selector:
    matchLabels:
      app: kong
# During a rolling update or node drain, Kubernetes will not remove a pod
# if it would bring the running count below 2.
# This prevents accidental full outage during deployments.
```

## The GitOps Flow — How Config Changes Reach Kong

This is the production workflow. No one manually runs `deck sync` from their laptop.

```
Developer edits kong.yml
      │
      ▼
Git commit + push to feature branch
      │
      ▼
Pull Request opened
      │
      ▼
CI Pipeline runs:
  deck validate kong.yml          ← check YAML is valid
  deck diff --kong-addr http://kong-admin:8001  ← show what will change
      │
      ▼
PR reviewed and merged to main
      │
      ▼
CD Pipeline runs:
  deck sync kong.yml --kong-addr http://kong-admin:8001
      │
      ▼
Kong Admin API (port 8001) receives the changes
      │
      ▼
PostgreSQL updated
      │
      ▼
All Kong nodes pick up new config within seconds
      │
      ▼
Zero downtime. Zero restarts. Zero manual steps.
```

### GitHub Actions example

```yaml
# .github/workflows/kong-deploy.yml

name: Deploy Kong Config

on:
  push:
    branches: [main]
    paths:
      - 'kong.yml'                  # only run when kong.yml changes

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install decK
        run: |
          curl -sL https://github.com/kong/deck/releases/download/v1.37.0/deck_1.37.0_linux_amd64.tar.gz -o deck.tar.gz
          tar -xf deck.tar.gz -C /tmp
          sudo cp /tmp/deck /usr/local/bin/

      - name: Validate Kong config
        run: deck validate kong.yml

      - name: Show diff (what will change)
        run: deck diff kong.yml --kong-addr ${{ secrets.KONG_ADMIN_URL }}

      - name: Sync to Kong
        run: deck sync kong.yml --kong-addr ${{ secrets.KONG_ADMIN_URL }}
        env:
          KONG_ADMIN_URL: ${{ secrets.KONG_ADMIN_URL }}
          # KONG_ADMIN_URL is stored as a GitHub secret
          # It points to the internal Kong admin endpoint
          # Never expose port 8001 to the internet
```

## Scaling Your Application (The Targets) — Independent of Kong

This is the key insight you already had. Kong and your app scale independently.

### Option 1 — Static Targets (manual, simple)

```yaml
# kong.yml — add targets manually when you scale your app
upstreams:
  - name: my-app-upstream
    targets:
      - target: 10.0.1.10:3000   weight: 100
      - target: 10.0.1.11:3000   weight: 100   # new instance
      - target: 10.0.1.12:3000   weight: 100   # another new instance

# Run: deck sync kong.yml
# Kong immediately starts load balancing across all 3.
# No Kong restart. No downtime.
```

### Option 2 — DNS-Based Upstream (automatic, zero config change) ← Recommended

```yaml
# kong.yml — point to a DNS name instead of IPs
services:
  - name: my-app
    host: my-app.internal           # internal DNS name
    port: 3000
    protocol: http
```

```
How it works:

Your app scales from 2 to 5 pods in Kubernetes
      │
      ▼
Kubernetes Service DNS (my-app.internal) updates automatically
      │
      ▼
Kong resolves DNS on each request
      │
      ▼
New pods are included automatically
      │
      ▼
No deck sync needed. No Kong config change. Nothing.
```

This is the cleanest approach when your app runs on Kubernetes.
The Kubernetes Service acts as the load balancer for your app.
Kong just talks to the Service DNS name.

### Option 3 — Kong Upstream + Kubernetes (hybrid)

```
Kong Upstream → points to Kubernetes Service ClusterIP
Kubernetes Service → load balances across your app pods

Kong handles:  auth, rate limiting, routing, plugins
K8s handles:   app pod scaling, health checks, rolling updates
```

## The Redis Requirement for Multi-Node Kong

This is a critical detail that trips people up.

```
Single Kong node:
  Rate limit counters stored in local memory
  Works perfectly

Multiple Kong nodes (what you have in production):
  Node 1 has its own counter: user X = 5 requests
  Node 2 has its own counter: user X = 5 requests
  Node 3 has its own counter: user X = 5 requests

  User X actually made 15 requests total.
  But each node thinks they only made 5.
  Your rate limit of 10/minute is effectively 30/minute.
  BROKEN.
```

The fix: use Redis as the shared counter store.

```yaml
# In your kong.yml rate-limiting plugin config
- name: rate-limiting
  config:
    minute: 10
    policy: redis                   # ← change from local to redis
    redis:
      host: your-elasticache-endpoint.cache.amazonaws.com
      port: 6379
      password: your_redis_password
      ssl: true                     # always use SSL in production
```

```
Now all Kong nodes write to the same Redis.
User X makes 10 requests spread across 3 Kong nodes.
Redis counter: user X = 10. Limit hit. 429 returned.
Accurate. Correct. Production-ready.
```

## Decision Matrix — Which Path for You?

```
Are you on Kubernetes (EKS/GKE/AKS)?
  YES → Use EKS + Helm + HPA                    ← recommended
  NO  → Are you on AWS?
          YES → Use EC2 + ASG + ALB
          NO  → Use EC2 + ASG + HAProxy (on-prem)

Do you need a GUI to manage Kong?
  YES → DB Mode (PostgreSQL) is required
  NO  → DB-less is an option (but DB Mode is still better for teams)

Do you run multiple Kong nodes?
  YES → Redis is required for accurate rate limiting
  NO  → Local policy is fine

Do you want Kubernetes-native config (CRDs instead of YAML)?
  YES → Consider Envoy Gateway (newer, less mature)
  NO  → Stick with Kong + decK YAML
```

## Summary — What to Tell Your Manager

```
1. Kong nodes are stateless.
   All config lives in PostgreSQL (RDS Multi-AZ).
   Add nodes freely — they connect to Postgres and start serving immediately.

2. Scaling Kong:
   On EKS → HPA scales pods in seconds based on CPU/memory.
   On EC2  → ASG scales instances in minutes based on CPU/RPS.

3. Scaling your app:
   Completely independent of Kong.
   Use DNS-based upstream — Kong resolves DNS per request.
   New app pods appear automatically. No Kong config change needed.

4. High Availability:
   3 Kong nodes minimum, spread across 3 AZs.
   RDS Multi-AZ for Postgres (auto-failover in ~60s).
   ElastiCache for Redis (shared rate limit counters).
   PodDisruptionBudget ensures rolling updates never kill all pods.

5. Config management:
   Everything in kong.yml, stored in Git.
   CI validates. CD runs deck sync.
   No manual curl commands. No SSH. No surprises.

6. Load balancer:
   ALB in front of Kong for HTTP APIs (TLS termination, health checks).
   NLB if you need WebSocket or gRPC at scale.
   HAProxy is an alternative for on-prem or very custom LB needs.

7. Envoy Gateway:
   Valid future option for fully Kubernetes-native teams.
   Kong is more mature, has a richer plugin ecosystem, and is the right
   choice for Kong-as-a-service across multiple teams today.
```
