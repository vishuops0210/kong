# Kong API Gateway — Production POC
> Deploy Kong as independent infrastructure first.
> Then tell it where your apps live. That's it.

---

## The Right Mental Model

Most people make the mistake of thinking Kong and the application are coupled.
They are not.

```
Kong is infrastructure like a load balancer or a firewall.
You deploy it once. It runs forever.
You tell it about apps via config (kong.yml + deck sync).
Apps can be anywhere. Same cluster. Different cluster. Bare metal. Another cloud.
Kong does not care.
```

So this POC has two phases:

```
Phase 1 — Deploy Kong as standalone infrastructure
           Get it running, healthy, HA, connected to Postgres and Redis.
           No application needed. Kong just sits there ready.

Phase 2 — Register your apps with Kong
           Run deck sync with a kong.yml that points to your app.
           Kong immediately starts routing, authenticating, rate limiting.
           The app itself is untouched. Zero changes to the app.
```

This is the correct order. This is what you show your manager.

## 1. Workload Classification

### Stateful vs Stateless

```
Kong Gateway Nodes     STATELESS
  No config stored on the node itself.
  All config lives in PostgreSQL.
  All rate limit counters live in Redis.
  A node can crash and restart with zero data loss.
  Add nodes freely — they self-configure from Postgres on startup.

PostgreSQL (RDS)       STATEFUL — critical
  Stores everything Kong knows: services, routes, plugins, consumers.
  Must be Multi-AZ. Must have automated backups.
  Loss = Kong cannot reload config. Existing nodes keep serving from cache.

Redis (ElastiCache)    STATEFUL — soft
  Stores rate limit counters only.
  Loss is tolerable (fault_tolerant: true in plugin config).
  Cluster mode with replicas recommended.
```

### Traffic Pattern

```
Read-heavy.
Every request → Kong reads from in-memory config cache. Postgres not touched.
Config writes → only when deck sync runs (rare, on config change only).
Pattern: ~99% reads / ~1% writes
```

### Public / Private / Protected

```
Public     → Kong Proxy :8000 / :8443
             Reachable from internet via Load Balancer only.
             TLS terminated at the Load Balancer.

Private    → Kong Admin API :8001
             NEVER exposed to internet.
             Reachable only from within the VPC.
             CI/CD pipeline reaches it via internal endpoint.

Private    → PostgreSQL :5432 and Redis :6379
             Private subnets. No public IPs. VPC only.

Protected  → Kong Manager UI :8002
             Whitelisted office IPs only via Security Group rule.
```

### T-Shirt Sizing

```
┌──────┬──────────────────────────────┬──────────┬────────┬───────────────────┐
│ Size │ Traffic                      │ CPU/node │ RAM    │ Kong Nodes        │
├──────┼──────────────────────────────┼──────────┼────────┼───────────────────┤
│ S    │ < 100 RPS, 2–3 services      │ 500m     │ 512Mi  │ 2 (min HA)        │
│ M    │ 100–500 RPS, 5–10 services   │ 1000m    │ 1Gi    │ 3 across 3 AZs    │
│ L    │ 500–2000 RPS, 10–20 services │ 2000m    │ 2Gi    │ 5 across 3 AZs    │
│ XL   │ 2000+ RPS, 20+ services      │ 4000m    │ 4Gi    │ 10+ (HPA driven)  │
├──────┼──────────────────────────────┼──────────┼────────┼───────────────────┤
│ RDS  │ S/M → db.t3.medium           │ L → db.r6g.large  │ XL → db.r6g.xlarge│
│ Redis│ S/M → cache.t3.medium        │ L/XL → cache.r6g.large cluster mode   │
└──────┴──────────────────────────────┴──────────┴────────┴───────────────────┘
```

## 2. The Three Deployment Approaches

```
Approach 1 — EC2 + ALB + Auto Scaling Group
Approach 2 — AWS EKS + HPA                  ← Recommended

```

All three deploy **only Kong** in Phase 1.
The application is registered in Phase 2 via kong.yml regardless of which approach you pick.

#### Step 1 — Provision RDS and ElastiCache first

Kong needs Postgres before it can start. Provision these before touching EC2.

```bash
# RDS PostgreSQL — Multi-AZ, private subnet group
aws rds create-db-instance \
  --db-instance-identifier kong-postgres \
  --db-instance-class db.t3.medium \
  --engine postgres \
  --engine-version 15.4 \
  --master-username kong \
  --master-user-password "$(aws secretsmanager get-secret-value \
      --secret-id kong/pg-password --query SecretString --output text)" \
  --allocated-storage 20 \
  --db-subnet-group-name kong-private-subnet-group \
  --vpc-security-group-ids sg-rds-kong \
  --multi-az \
  --backup-retention-period 7 \
  --no-publicly-accessible

# ElastiCache Redis — cluster mode, private subnet
aws elasticache create-replication-group \
  --replication-group-id kong-redis \
  --description "Kong rate limit store" \
  --cache-node-type cache.t3.medium \
  --engine redis \
  --num-cache-clusters 3 \
  --security-group-ids sg-redis-kong \
  --cache-subnet-group-name kong-private-subnet-group \
  --at-rest-encryption-enabled \
  --transit-encryption-enabled
```

#### Step 2 Store secrets in HashiCorp Vault

```bash
# Postgres password
vault kv put secret/kong/postgres \
  password="$(openssl rand -base64 32)"

# Kong will read this via Ansible at provisioning time
# Never hardcoded in any file. Never in Git.
```

#### Step 3 Provision EC2 via Ansible (no manual SSH)

```yaml
# ansible/kong-ec2.yml
---
- name: Deploy Kong on EC2
  hosts: kong_nodes
  become: true

  vars:
    kong_version: "3.9.0"
    pg_host: "{{ lookup('aws_ssm', '/kong/rds_endpoint') }}"
    pg_password: "{{ lookup('hashi_vault', 'secret/kong/postgres:password') }}"
    redis_host: "{{ lookup('aws_ssm', '/kong/redis_endpoint') }}"

  tasks:
    - name: Download Kong
      get_url:
        url: "https://packages.konghq.com/public/gateway-39/deb/ubuntu/pool/noble/main/k/ko/kong_{{ kong_version }}/kong_{{ kong_version }}_amd64.deb"
        dest: /tmp/kong.deb

    - name: Install Kong
      apt:
        deb: /tmp/kong.deb

    - name: Write kong.conf
      template:
        src: templates/kong.conf.j2
        dest: /etc/kong/kong.conf
        mode: '0640'

    - name: Bootstrap database (run once on first node only)
      command: kong migrations bootstrap -c /etc/kong/kong.conf
      run_once: true

    - name: Enable and start Kong
      systemd:
        name: kong
        state: started
        enabled: true
```

```ini
# templates/kong.conf.j2
database          = postgres
pg_host           = {{ pg_host }}
pg_port           = 5432
pg_database       = kong
pg_user           = kong
pg_password       = {{ pg_password }}

proxy_listen      = 0.0.0.0:8000
admin_listen      = 127.0.0.1:8001
status_listen     = 0.0.0.0:8100

nginx_worker_processes = auto
mem_cache_size    = 256m
log_level         = notice

proxy_access_log  = /usr/local/kong/logs/access.log
proxy_error_log   = /usr/local/kong/logs/error.log
```

#### Step 4 — ASG Scaling Policy

```
Scale OUT:  CPU > 60% for 2 minutes  →  add 1 EC2
Cooldown:   3 minutes
Scale IN:   CPU < 30% for 10 minutes →  remove 1 EC2
Cooldown:   5 minutes

Min: 2 nodes (HA — never single node)
Max: 10 nodes (cost cap)

Scale speed: 3–5 minutes (EC2 boot + Kong start)
             Reduce to ~90s with pre-baked AMI
```

#### Step 5 — Verify Kong is healthy

```bash
# From inside the VPC (bastion or CI runner)
curl http://<ec2-private-ip>:8100/status
# Expected: {"database":{"reachable":true},...}

curl http://<alb-dns>:8000
# Expected: {"message":"no Route matched with those values"}
# This means Kong is running and waiting for config. Perfect.
```

### Approach 2 — AWS EKS + HPA ← Recommended

#### Architecture

```
            Internet
                │
      ┌─────────▼───────────┐
      │      AWS ALB        │  AWS Load Balancer Controller
      │  TLS via ACM cert   │  health checks Kong on :8100
      └─────────┬───────────┘
                │
      ┌─────────▼───────────────────────────────┐
      │           EKS Cluster                   │
      │                                         │
      │   Kong Pod (AZ-a)  ← HPA manages these  │
      │   Kong Pod (AZ-b)    min: 3  max: 20    │
      │   Kong Pod (AZ-c)                       │
      │                                         │
      │   Admin API → ClusterIP (VPC only)      │
      └─────────┬───────────────────────────────┘
                │
   ┌────────────┼────────────┐
   ▼                         ▼
┌──────────────┐    ┌──────────────┐
│ RDS Postgres │    │ ElastiCache  │
│ Multi-AZ     │    │ Redis Cluster│
│ Private subnet│   │ Private subnet│
└──────────────┘    └──────────────┘
```

#### Step 1 — Create EKS Cluster

```bash
eksctl create cluster \
  --name kong-production \
  --region ap-south-1 \
  --nodes 3 \
  --node-type t3.medium \
  --nodes-min 3 \
  --nodes-max 10 \
  --managed
# ~15 minutes. Creates 3 worker nodes, one per AZ, automatically.
```

#### Step 2 — Create namespace and store secrets

```bash
kubectl create namespace kong

# Postgres password from Vault — never hardcoded
kubectl create secret generic kong-postgres-secret \
  --namespace kong \
  --from-literal=pg_password="$(vault kv get -field=password secret/kong/postgres)"

# Redis auth token
kubectl create secret generic kong-redis-secret \
  --namespace kong \
  --from-literal=redis_password="$(vault kv get -field=password secret/kong/redis)"
```

#### Step 3 — Install Kong via Helm

```bash
helm repo add kong https://charts.konghq.com
helm repo update

helm install kong kong/kong \
  --namespace kong \
  --values kong-values.yaml
```

```yaml
# kong-values.yaml — Kong only, no application config here

image:
  repository: kong/kong-gateway
  tag: "3.9.0"          # pinned — never latest in production

replicaCount: 3         # 3 pods to start, HPA takes over from here

env:
  database: postgres
  pg_host: your-rds-endpoint.ap-south-1.rds.amazonaws.com
  pg_port: 5432
  pg_database: kong
  pg_user: kong
  pg_password:
    valueFrom:
      secretKeyRef:
        name: kong-postgres-secret
        key: pg_password

  proxy_listen: "0.0.0.0:8000"
  admin_listen: "0.0.0.0:8001"    # ClusterIP — not reachable outside cluster
  status_listen: "0.0.0.0:8100"   # Kubernetes probes hit this

  nginx_worker_processes: auto
  mem_cache_size: 256m

# Public proxy — ALB created automatically
proxy:
  enabled: true
  type: LoadBalancer
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "alb"
    service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"
    service.beta.kubernetes.io/aws-load-balancer-certificate-arn: "arn:aws:acm:ap-south-1:ACCOUNT:certificate/xxx"

# Admin API — internal only, CI/CD reaches via port-forward
admin:
  enabled: true
  type: ClusterIP

# Kubernetes will not send traffic until readiness passes
readinessProbe:
  httpGet:
    path: /status
    port: 8100
  initialDelaySeconds: 15
  periodSeconds: 10

# Kubernetes restarts pod if liveness fails
livenessProbe:
  httpGet:
    path: /status
    port: 8100
  initialDelaySeconds: 30
  periodSeconds: 10

# Always set resource limits — never let a pod consume the whole node
resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "2000m"
    memory: "1Gi"

# Force one pod per AZ — AZ failure = 2 pods still serving
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
            - key: app
              operator: In
              values: [kong]
        topologyKey: topology.kubernetes.io/zone

# Rolling updates never drop below 2 running pods
podDisruptionBudget:
  enabled: true
  minAvailable: 2
```

#### Step 4 — Apply HPA

```yaml
# hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: kong-hpa
  namespace: kong
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: kong-kong
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 70
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120
```

```bash
kubectl apply -f hpa.yaml
kubectl apply -f pdb.yaml
```

#### Step 5 — Verify Kong is healthy

```bash
# Check pods are running across all 3 AZs
kubectl get pods -n kong -o wide
# NAME                    READY   STATUS    NODE
# kong-kong-xxx-aaa       1/1     Running   ip-10-0-1-x (AZ-a)
# kong-kong-xxx-bbb       1/1     Running   ip-10-0-2-x (AZ-b)
# kong-kong-xxx-ccc       1/1     Running   ip-10-0-3-x (AZ-c)

# Get the Load Balancer URL
kubectl get svc kong-kong-proxy -n kong
# EXTERNAL-IP: a1b2c3.ap-south-1.elb.amazonaws.com

# Hit Kong — it's running but knows nothing yet
curl http://a1b2c3.ap-south-1.elb.amazonaws.com
# {"message":"no Route matched with those values"}
# Kong is live. Waiting for config. Phase 1 complete.
```

#### Step 2 — ECS Service + Auto Scaling

```bash
# Create ECS service with 3 tasks spread across AZs
aws ecs create-service \
  --cluster kong-cluster \
  --service-name kong-gateway \
  --task-definition kong-gateway:1 \
  --desired-count 3 \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={
    subnets=[subnet-aaa,subnet-bbb,subnet-ccc],
    securityGroups=[sg-kong],
    assignPublicIp=DISABLED
  }" \
  --load-balancers "targetGroupArn=arn:...,containerName=kong,containerPort=8000"

# Register auto scaling
aws application-autoscaling register-scalable-target \
  --service-namespace ecs \
  --resource-id service/kong-cluster/kong-gateway \
  --scalable-dimension ecs:service:DesiredCount \
  --min-capacity 3 \
  --max-capacity 15

# Scale on CPU > 60%
aws application-autoscaling put-scaling-policy \
  --policy-name kong-cpu-scaling \
  --service-namespace ecs \
  --resource-id service/kong-cluster/kong-gateway \
  --scalable-dimension ecs:service:DesiredCount \
  --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration '{
    "TargetValue": 60.0,
    "PredefinedMetricSpecification": {
      "PredefinedMetricType": "ECSServiceAverageCPUUtilization"
    },
    "ScaleOutCooldown": 60,
    "ScaleInCooldown": 300
  }'
```
