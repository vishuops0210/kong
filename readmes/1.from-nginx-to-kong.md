# 1. Introduction

Modern API infrastructure did not emerge overnight.

The journey from **NGINX** to **OpenResty** and finally to **Kong** represents the evolution of web infrastructure from:

```text
High-performance networking
→ Programmable request processing
→ Full-scale API gateway platforms
```

Understanding this evolution helps explain:

- Why OpenResty was created
- Why Lua became important in networking
- Why Kong exists today
- How modern API gateways are architected internally

---

# 2. NGINX — The High-Performance Networking Engine

NGINX was originally designed as a lightweight and extremely efficient web server focused on handling large numbers of concurrent connections.

Its core responsibilities included:

- Reverse Proxying
- Load Balancing
- Static File Serving
- TLS/SSL Termination
- Request Routing
- HTTP Caching

NGINX achieved exceptional performance because of its:

- Event-driven architecture
- Non-blocking asynchronous I/O
- Low memory footprint
- Efficient worker process model

At its core, NGINX was optimized to solve networking problems efficiently.

```text
NGINX was primarily a networking engine,
not an application logic engine.
```

---

# 3. The Shift Toward APIs and Microservices

As software systems evolved into:

- APIs
- Microservices
- SaaS platforms
- Multi-tenant systems
- Cloud-native architectures

new requirements started emerging at the gateway layer.

Organizations needed capabilities such as:

- JWT validation
- OAuth authentication
- API key verification
- Dynamic rate limiting
- Redis-backed policies
- Database-driven authorization
- Request/response transformation
- Service discovery
- Traffic policies
- Observability and tracing

Traditional NGINX configuration became increasingly insufficient for these programmable workflows.

---

# 4. Limitations of Traditional NGINX Extensibility

Before OpenResty existed, developers generally had three approaches for extending NGINX behavior.

## 4.1 Native NGINX Modules

NGINX already provided built-in modules for:

- Basic authentication
- URL rewrites
- Static rate limiting
- Proxy configuration

However, these modules were:

- Static
- Configuration-heavy
- Difficult to customize dynamically
- Limited for complex business logic

---

## 4.2 Writing Custom C Modules

Since NGINX itself is written in C, developers could extend it by creating custom C modules.

This approach was extremely powerful, but operationally difficult.

It required:

- Deep understanding of NGINX internals
- Knowledge of event-driven systems
- Manual memory management
- Recompilation of NGINX
- Careful handling of crashes and memory safety

Although performant, this approach significantly increased engineering complexity.

---

## 4.3 External Authorization or Business Services

Another common architecture involved delegating logic to external services.

### Traditional Flow

```text
Client
   ↓
NGINX
   ↓
External Auth Service
   ↓
Database / Redis
   ↓
Backend Service
```

This design solved flexibility problems but introduced new operational costs:

- Additional network hops
- Increased latency
- More infrastructure
- Higher operational complexity
- Additional service management overhead

---

# 5. OpenResty — Making NGINX Programmable

OpenResty fundamentally changed the architecture by allowing developers to execute programmable logic directly inside the NGINX request lifecycle.

OpenResty combines:

```text
NGINX
+ LuaJIT
+ ngx_lua module
+ Asynchronous Lua APIs
```

This transformed NGINX from:

```text
A high-performance reverse proxy
```

into:

```text
A programmable API execution platform
```

---

# 6. Understanding Lua and LuaJIT

## 6.1 Lua

Lua is a lightweight embeddable scripting language designed to be integrated into larger systems.

It is widely used for:

- Embedded scripting
- Plugin systems
- Runtime extensibility
- Lightweight programmable workflows

Lua itself is written in C and was intentionally designed for embedding.

---

## 6.2 LuaJIT

LuaJIT is a high-performance runtime implementation of Lua.

It includes:

- Just-In-Time (JIT) compilation
- Highly optimized execution
- Low-overhead runtime performance

LuaJIT is implemented primarily in:

- C
- Assembly

and can execute Lua code at near-native speeds.

### Important Distinction

```text
Lua      = Programming Language
LuaJIT   = Runtime Engine for Lua
```

Comparable example:

```text
JavaScript = Language
V8         = JavaScript Runtime Engine
```

---

# 7. Internal Architecture of OpenResty

OpenResty embeds the LuaJIT runtime directly inside NGINX worker processes.

### Internal Worker Architecture

```text
NGINX Worker Process
   ├── Event Loop
   ├── HTTP Processing Engine
   ├── Proxy Engine
   └── Embedded LuaJIT VM
            └── Executes Lua Scripts
```

This design is extremely important because:

```text
Lua does NOT run as an external service.

Lua executes INSIDE the NGINX worker process itself.
```

This eliminates additional network hops and preserves the performance characteristics of NGINX.

---

# 8. Request Lifecycle in OpenResty

With OpenResty, request processing becomes programmable.

### Request Flow

```text
Client Request
      ↓
NGINX Receives Request
      ↓
Lua Logic Executes Inside Worker
      ↓
Authentication / Authorization
      ↓
Redis or Database Access
      ↓
Rate Limiting / Policy Evaluation
      ↓
NGINX Proxies Request
      ↓
Response Returned
```

This architecture enabled developers to build sophisticated API processing pipelines directly within the gateway layer.

---

# 9. The Remaining Challenges

Although OpenResty introduced programmability, building a complete API gateway platform still required substantial engineering effort.

Teams still needed to implement:

- Plugin management
- Dynamic routing
- Authentication frameworks
- Monitoring systems
- Observability pipelines
- Distributed configuration
- Service discovery
- Deployment tooling
- Administrative APIs
- Multi-node synchronization

OpenResty provided the runtime foundation, but not the complete platform experience.

---

# 10. Kong — Productizing OpenResty

Kong was built on top of OpenResty to provide a production-ready API gateway platform.

Instead of manually writing Lua scripts for every capability, Kong introduced:

- Plugin architecture
- Admin APIs
- Declarative configuration
- Authentication plugins
- Rate limiting plugins
- Logging and observability
- Traffic control policies
- Service and route management
- Cluster configuration management

Kong effectively transformed OpenResty into an enterprise-grade API gateway ecosystem.
